## Decisions (named, do not reopen)

1. `resolveCuration` decisions: `apply` (apply the proposal, optionally with `mergedTitle`/`mergedContent` overriding a `merge` draft), `reject`, `flag`. For `flag`, `itemId` is a KNOWLEDGE ENTRY id and `reason` is required: it creates a new `curation_actions` row `kind:'flag'`, `actor:'agent:<platform>'`, `status:'proposed'`, entry_ids `[itemId]`, payload `{reason}`; applying a `flag` only marks it applied (no entry change); undo reverts the status.
2. Agent actions record `actor = 'agent:' + platform`, where platform is `COGNISTORE_PLATFORM` allowlisted to `claude-code|copilot|opencode`, anything else becomes `unknown` (same as the provenance resolver); a test passes a hostile value and expects `agent:unknown`.
3. `getCurationQueue` default limit 10, max 25; each action carries at most 3 entries with `content` truncated to 600 chars.
4. Agent maintenance state: `~/.cognistore/curation-state.json` = `{ "pending": <int>, "scopes": {"<scope>": <int>}, "updatedAt": "<iso>" }` written by the sidecar (async fs, only when the value changes); `~/.cognistore/agent-maintenance.json` = `{ "lastAt": "<iso>" }` written by the MCP server after a successful `resolveCuration`. The Stop hook suggests `/cognistore-maintain` only if pending for the cwd scope > 5, lastAt older than 24 h or absent, and no suggestion was shown in the last 24 h (marker file under `~/.cognistore/hooks-state/`).
5. `resolveCuration` joins `COGNISTORE_DENY_TOOLS` (user decides whether to allow it); `getCurationQueue` and `supersedeKnowledge` do not.
6. The old cleanup data migrates inside migration 2.4.6 (INSERT ... SELECT, idempotent, `kind` preserved or mapped to `merge`/`remove`, `actor:'legacy-cleanup'`, `status:'proposed'`); the old routes keep responding.
